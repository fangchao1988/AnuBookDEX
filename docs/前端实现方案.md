# AleoBook DEX 前端实现方案

> 原型依据：`static/prototype_aleo.html`（1898 行完整原型，7 视图 + 4 模态框）
> 后端依据：`internal/dex/ws/`（WebSocket Hub，channel 订阅式广播）、`internal/core/market/`、`internal/core/l2quote/`（行情结构体）

## 1. 概述

将 `prototype_aleo.html` 原型落为生产级 React 单页应用，与 Go 引擎的 DEX 双链架构（Anubis EVM + Aleo snarkOS）对接。前端保持与后端一致的"双链适配器"思路：**行情链路统一走 WebSocket，交易链路按链走适配器（viem / Aleo SDK），UI 与链无关**。

### 1.1 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 构建 | **Vite 5 + React 18 + TypeScript 5** | HMR 快、TS 原生 |
| 样式 | **Tailwind CSS 3** | 原型是 CSS 变量体系，token 化后可直接映射 |
| 路由 | React Router v6 | 7 个视图 + 参数化交易对（`/trade/:symbol`） |
| 状态 | **Zustand**（行情）+ TanStack Query（REST 数据） | 行情高频更新必须外部 store，避免 Context 全树重渲染 |
| 图表 | **Lightweight Charts**（K线/指标）+ 自绘 canvas 深度图 | TradingView 生态；Lightweight Charts 免费、无 WebGL 依赖、增量 update 性能好。深度图 LWC 无内置，用轻量 canvas 自绘（~150 行） |
| Web3 | **viem**（Anubis EVM 链）+ **Aleo SDK**（Leo Wallet / Piecrust） | 见 §7：Ethers.js/Viem 仅覆盖 EVM；Aleo 链需 Leo 钱包适配器，统一收口在 WalletProvider 抽象后 |
| 数据请求 | TanStack Query v5 + 自研 WS 客户端 | 后端 WS 是手写协议（token 鉴权 + channel 订阅），需薄封装 |
| 测试 | Vitest + Testing Library；E2E Playwright | |
| 精度 | decimal.js | 对齐后端 shopspring/decimal（37 位精度），**禁止 float64** 计算价格数量 |

> 说明：用户给定"Ethers.js/Viem"二选一，**推荐 viem**（更小、TS 优先、EIP-1193 支持好）。若团队更熟 Ethers v6 也可，WalletProvider 接口（§7.1）保证可替换。

## 5. 数据层设计

### 5.1 WebSocket 协议（P2 已实测确认）

连接：`ws://<host>/ws?token=<jwt>&client_id=<uuid>`（后端也接受 `Authorization` header）。后端 `auth.ValidateToken` 校验（`auth.token` 未配置时放行），未通过返回 401。

订阅帧（后端 `internal/dex/ws/client.go` `readPump` 已实现，字段为 **`cmd`** 而非 `op`）：

```json
{ "cmd": "subscribe", "channels": ["depth.BTC_USDT", "kline.BTC_USDT.1min", "trade.BTC_USDT"] }
{ "cmd": "unsubscribe", "channels": [...] }
```

**服务端推送无信封**，客户端按 payload 内容推断频道（前端 `lib/ws/client.ts` `inferChannel`）：

| payload.type | 推断频道 | Payload（后端 json 字段，P2 实测） |
|---|---|---|
| `market.orderBook` | `depth.{symbol}` | `{seqId, id, bids: [[price, qty]...], asks: [...], ts, version, type, pairCode}`（全量快照帧，直接整体替换） |
| `market.candles` | `kline.{symbol}.{interval}` | `{type, pairCode, interval, data: {id, seqId, open, high, low, close, turnOver, vol, count}, id, SeqId}` |
| `market.fills` | `trade.{symbol}` | `{id, ts, type, pairCode, data: [{vol, ts, id, price, direction}]}` |
| `market.ticker` | `ticker.{symbol}` | `{type, pairCode, interval, data: {id, seqId, open, close, high, low, vol, turnOver, askPrice, askVol, bidPrice, bidVol, change, changePercent}, id, SeqId}` |

**符号命名**：后端 channels 用下划线（`BTC_USDT`，config `symbols`），前端展示用斜杠（`BTC/USDT`）、路由用拼接（`BTCUSDT`），映射在 `web/src/lib/symbol.ts`。

客户端 WS 封装（`web/src/lib/ws/client.ts`）已实现：
- 指数退避重连（1s→30s 封顶）+ 重连后自动重订阅全部频道；
- 服务端每 ~54s 发 Ping，浏览器协议层自动回 Pong，无需应用层心跳；
- 页面 `visibilitychange` 恢复时主动重连；`wsClient.onMessage` 全局分发到 marketStore。

**后端 P2 改动**（均已在仓库落地）：
- `internal/dex/ws/hub.go`：新增 `BroadcastRaw(channel, data)`，广播已序列化字节；
- `internal/core/l2quote/rabbitmq_ops.go`：新增 `RawPublisher` 注入点 + `SetRawPublisher`，`sendToMQ` 在 RabbitMQ 未初始化时按 routing key（`market.{symbol}.kline.{interval}` / `trade.detail` / `ticker`）映射到 WS 频道直连 Hub；
- `internal/dex/runner/engine.go`：`l2.SetRawPublisher(hub.BroadcastRaw)` 接线；
- **本地联调**：`chain.<chain>.simulate-orders=true` 启用 `runner.SimOrderSource`（随机限价单驱动 撮合→l2quote→WS 全链路），配置见 `conf/dev-anubis-sim.yaml`。

### 5.2 行情 Store 与渲染节流

- `marketStore` 以 `symbol` 为 key 存 `{bids: Map<price, qty>, asks: Map, lastTrades[], klines: Map<interval, Candle[]>, ticker}`；
- **深度增量合并**（`lib/ws/orderbook.ts`）：后端起深度广播包含完整 bids/asks（`QuoteDepths`），前端按 seqId 排序取最新帧全量替换（简单可靠）；若后续后端改 diff 帧，算法层预留 merge 接口；
- **渲染节流**：深度帧频率高（撮合引擎 100ms 级推送），store 更新用 rAF 合并，**表格 DOM 更新每个 symbol 每帧最多一次**；订单簿 20 档以内全渲染，全量深度（500+ 档）用 `@tanstack/react-virtual` 虚拟滚动；
- 数字一律 `decimal.js` 字符串往返（`lib/decimal.ts`），渲染时按 `symbol-info`（精度档位）格式化。

### 6.1 关键交互流程

1. **下单**：表单校验 → 按隐私模式路由（标准=REST 明文；隐私=前端用 Aleo 公钥做 Note 承诺加密后再提交；暗池=MPC 参数包装）→ 钱包签名（viem/Aleo）→ POST 订单 → WS 收到自己订单的撮合回执后更新委托列表；
2. **隐私模式切换**（原型方案1）：常量表驱动说明文案与指标（速度/暴露/MEV 防护），UI 层纯展示，链上行为差异收敛在 `orderAdapter`（§7.4）；
3. **暗池预估**（方案2）：前端本地实时计算（金额/深度 → 撮合概率、时长、AI 冰山拆分建议），公式照搬原型 `updateDarkpoolEstimate()`，数据源改为实时 `depth` store 而非硬编码常量；
4. **杠杆分层**（方案3）：四 tier 卡片（保守/稳健/激进/专业），滑块↔tier 双向联动，随 tier 更新维持保证金率/强平价/最大持仓量（公式 `liq = entry * (1 - 1/lev)`）；
5. **AI 自动减仓边界**（方案4/5）：默认关闭；开启后展示边界控件（阈值/单次比例/日次数/最低保留/执行方式/时段），配置持久化到 `/api/v1/ai/bounds`；AI 日志表格从该接口 + WS 事件渲染。

## 7. Web3 钱包层（双链适配）

> 关键事实：**Ethers.js/viem 是 EVM 生态工具，Aleo 链钱包（Leo Wallet SDK）不是 EIP-1193 兼容**。因此仿照后端 `internal/dex/chain` 的 ChainAdapter 思路，前端做同样的双链抽象，避免 UI 层与链耦合。

### 7.1 WalletProvider 抽象

```ts
interface WalletProvider {
  chain: 'anubis' | 'aleo'
  connect(): Promise<Account>
  signMessage(msg: string): Promise<string>
  getBalance(asset: string): Promise<Decimal>
  getAddress(): string
  onAccountsChanged(cb): unsubscribe
}
```

### 7.2 适配器

- **AnubisAdapter（viem）**：`createWalletClient` + EIP-1193（MetaMask/Rabby/OKX/WalletConnect）；监听链上 `OrderSubmitted` 事件（内存记忆：真实 ABI 已核对）做订单上链确认。
- **AleoAdapter（Aleo SDK）**：`window.leoWallet`（Leo Wallet）或 Piecrust 注入；`requestRecords` 取余额、`requestTransaction` 广播 snarkOS transition（下单 = 调 `anubook_dex.aleo` program 的 `place_order` transition，隐私下单时先对 payload 做 Aleo 加密/承诺再上链）；用 `GET /v1/testnet/program/anubook_dex.aleo/mapping/orders/{id}u128` 轮询确认。

### 7.3 登录鉴权链

钱包签名挑战 → `POST /api/v1/auth/login` → 后端验签发 JWT → JWT 作为 `ws?token=` + REST `Authorization` → 前端存内存（localStorage 存加密会话，原型设置里有"会话超时自动登出"，实现为 30min 定时清除）。

### 7.4 下单双链路由（orderAdapter）

P3 已落地（Aleo 侧）：

```
OrderForm (链无关 UI)
   └─ submit()
        ├─ 钱包已连接(leo) -> wallet.placeOrder()         # place_order transition -> txId
        │     └─ GET /order/tx/{txId}（引擎代理 snarkOS） # 提取 Order record ciphertext
        └─ 钱包未连接/DevWallet -> 占位 ciphertext（联调；生产必须钱包）
        └─ POST /order（symbol/side/price/amount/token/trader/ciphertext）
              └─ 后端：OrderPool.RecordSubmit（等待中）
                    └─ 撮合 -> Settlement.SubmitBatch -> RecordMatch（更新状态/成交量）
                          └─ GET /api/v1/orders?trader=&symbol=（委托列表，前端 5s 轮询）
```

签名登录：**连接即登录**（地址身份 → localStorage `aleo_address` → WS/REST 身份）。签名挑战验签依赖后端 Aleo 验签能力（snarkVM 无 Go SDK，需后续用 Leo 合约/节点能力接入），前端 WalletProvider 已预留接口。

```
OrderForm (链无关 UI)
   └─ orderAdapter.submit(order, privacyMode)
        ├─ standard  → REST POST /api/v1/orders（引擎撮合）
        ├─ privacy   → Aleo 加密 Note → snarkOS transition → REST 关联
        └─ darkpool  → MPC 包装 → 暗池专用接口（额度 ≥10k USDT 二次确认）
```

## 8. 性能与工程化

- **虚拟滚动**：全量深度、历史委托、AI 日志列表（`@tanstack/react-virtual`）；
- **渲染节流**：rAF 合并高频 store 更新；订单簿行组件 memo 化（价格 key）；
- **WS 稳定性**：心跳、指数退避重连、断线恢复（重拉深度快照 REST 兜底）、页面 hidden 时暂停订阅（visibilitychange）；
- **数字安全**：统一 decimal.js，禁止 Number 运算价格；输入框校验按 symbol 精度截断；
- **可访问性/错误态**：skeleton、错误重试（TanStack Query）、WS 断开顶部横幅；

## 11. Aleo 侧适配（2026-08 实测）

- **行情**：Aleo 引擎（`cmd/engine/aleo`）复用 runner.StartEngine + ws.Hub，协议与 Anubis 完全一致，前端 P2 成果零改动复用；
- **订单**：`POST /order`（Phase 2b 链下通道）→ OrderPool → Subscriber → 撮合 → WS 行情。请求字段 `{order_id, side(0买/1卖), price, amount, base_token, quote_token, deadline, trader, ciphertext}`；`ciphertext` 为 Order record 密文（结算用），本地联调 `chain.aleo.require-ciphertext=false` 可空（生产默认必填）；
- **联调**：`CONFIG_FILE=./conf/dev-aleo.yaml ./engine-aleo` + 灌单脚本 `node web/scripts/sim-orders.mjs`（默认灌 ETH_USDT，token 1/2）；
- **已知限制**：aleo Subscriber 为单符号路由（firstSym，Phase 1 简化），多交易对订单会串到首个订阅的 symbol —— 联调时单交易对灌单（ETH_USDT）；
- **实测**：灌单 40 笔无崩溃；深度 96 帧/8s、K线 8 条（OHLCV 完整）、Ticker 8 条、交叉单立即触发 `market.fills`；vite 代理 `POST /order` 200 ok；
- **坑记录**：dev 配置数据目录必须与 Anubis 引擎隔离（旧快照的 OrderId 与 treemap 状态不兼容会触发 `cached key is not in cache` Fatal）；`scheduler.snapshot` 与 `symbol-info.default.depth-steps` 缺失会导致启动 panic。
