【验收 / 评分标准（唯一依据）】
{
1. 硬性门槛

1.1 文档与静态可验证性
- 是否提供了清晰的启动 / 运行 / 测试 / 配置说明
- 文档中的入口、配置和项目结构在静态上是否基本一致
- 交付物是否提供了足够静态证据，使人工评审者无需先改核心代码即可尝试验证

2. 交付完整性

2.1 是否构成一个从 0 到 1 的基础可交付项目，而不是局部功能、示例实现或代码片段
- 是否以 mock / hardcode 替代真实逻辑且没有说明
- 是否具备完整项目结构，而不是零散代码或单文件示例
- 是否提供了基础项目文档，例如 README 或等价说明

3. 工程与架构质量

3.1 项目结构与模块划分是否与问题规模相匹配
- 项目结构是否清晰，模块职责是否合理
- 是否存在明显冗余或无必要文件
- 是否将大量实现不合理地堆在单个文件中

3.2 是否具备基本可维护性和可扩展性，而不是临时堆砌式实现
- 是否存在明显混乱结构或高度耦合
- 核心逻辑是否预留扩展空间，而不是完全写死

4. 工程细节与专业度

4.1 工程细节与整体形态是否体现出专业软件实践，包括但不限于错误处理、日志、校验和 API 设计
- 错误处理是否基本可靠且对用户友好
- 日志是否有助于排查，而不是随意 print 或完全缺失
- 关键输入与边界条件是否具备必要校验

4.2 项目是否更像真实产品 / 服务，而不是示例或演示级实现
- 整体交付物是否更接近真实应用，而不是教学样例或 demo

5. 美观度（仅前端 / 全栈任务适用）

5.1 视觉与交互设计是否符合场景并具备基本视觉质量
- 页面不同功能区域是否能通过背景、间距、分隔或层级进行区分
- 整体布局是否合理，对齐、间距、比例是否基本协调
- UI 元素（文本、图片、图标等）是否正常显示
- 视觉元素是否与页面主题和文本内容一致，是否存在明显不匹配
- 是否具备基本交互反馈，如 hover、click、transition 等
- 字体、字号、颜色、图标风格是否基本一致，是否存在明显混搭
}

====================
硬性规则（必须遵守）

1）纯静态审查边界
- 仅进行静态分析。
- 不启动项目，不运行测试，不运行 Docker，不连接外部服务。
- 除非有直接静态证据（例如实现完整且测试明确覆盖），否则不得声称某个流程“运行时可正常工作”。
- 任何依赖真实运行、环境配置、网络访问、容器编排、浏览器交互、时间序列或外部集成的结论，必须标记为：
  - 无法通过静态审查确认
  - 或 需要人工验证

2）允许并推荐按风险优先扫描
- 你不需要按照六大验收章节的顺序扫描代码。
- 你可以按最利于速度与准确性的顺序进行扫描，但最终报告必须仍然按六大章节组织。
- 推荐扫描优先级如下：
  1. README / 文档 / 配置示例 / 包管理清单 / 环境变量示例
  2. 入口点与路由注册
  3. 认证 / 会话 / Token / 中间件 / 权限守卫
  4. 核心业务模块、服务、数据模型、持久层
  5. 管理 / 内部 / 调试端点
  6. 测试文件与测试配置
  7. 如适用，再看前端 UI 结构与视觉一致性

3）不要遗漏实质问题，但避免低价值重复
- 最终报告必须覆盖六大验收章节及其每个二级要求。
- 若某项不适用，标记为“不适用”，并简要说明边界。
- 若某项无法通过静态证据确认，标记为“无法通过静态审查确认”，并说明原因。
- 对重复症状应尽量合并为根因级问题。
- 不要因为同一个根因在很多文件里重复出现，就低价值地逐条展开。

4）证据必须可追溯
- 每个关键结论都必须给出精确证据，格式为 `file:line`，例如 `README.md:10` 或 `app/main.py:42`。
- 不得做无证据判断。
- Pass / Fail / Blocker / High 这类强结论不得建立在模糊印象上。
- “在已查看范围内未发现”不自动等于“仓库中不存在”；只有当已查看证据足以支持该结论时，才能判定“缺失”，否则必须使用“无法通过静态审查确认”。

5）每个判断都必须说明依据
- 对于 Pass / Partial Pass / Fail / 不适用 / 无法通过静态审查确认，每项都要给出简明且具体的理由。
- 理由可来源于：
  - 与验收标准的一致性
  - 与常见工程 / 架构实践的一致性
  - 代码实现级证据
  - 测试静态证据
  - 文档与代码的一致性证据

7）安全审查优先级最高
- 重点审查认证、鉴权、权限边界和数据隔离。
- 你必须显式检查并评估以下方面，并给出证据：
  - 认证入口
  - 路由级鉴权
  - 对象级鉴权
  - 函数级权限控制
  - 租户 / 用户数据隔离
  - 管理 / 内部 / 调试端点保护
- 如果某个安全风险有较强迹象但无法完全静态证实，必须标记为“疑似风险”或“无法通过静态审查确认”，不得夸大为已证实缺陷。

8）Mock / Stub / Fake 的处理
- Mock / Stub / Fake 行为本身不是缺陷，除非 AnuBook产品需求文档 明确要求真实第三方集成或真实生产行为。
- 但你仍然必须说明：
  - mock 是如何实现的
  - 在什么条件下启用
  - 是否存在误用于生产的风险
  - 是否因此导致校验或安全约束可被绕过

9）测试与日志是强制审查维度
- 你必须对单元测试、API / 集成测试、日志设计进行静态审查。
- 不自动运行它们。
- 你必须评估：
  - 是否存在
  - 静态上覆盖了什么
  - 是否覆盖核心流程和重要失败路径
  - 日志分类是否清晰有意义
  - 日志或响应中是否存在敏感信息泄漏风险

10）测试覆盖静态审计是强制项，但要以高风险为核心
- 先从 AnuBook产品需求文档 和实现中提炼核心业务需求与主要风险点。
- 然后将最重要的需求 / 风险点映射到现有测试。
- 重点关注：
  - 核心 happy path
  - 输入校验失败
  - 未认证 401
  - 未授权 403
  - 404 not found
  - 冲突 / 重复提交（如适用）
  - 对象级鉴权
  - 租户 / 用户隔离
  - 分页 / 排序 / 过滤（如适用）
  - 空数据 / 极值 / 时间字段 / 并发 / 重复请求 / 回滚（如适用）
  - 敏感日志泄漏
- 优先为高风险和核心需求区域建立覆盖映射。
- 不需要为了所有琐碎要求生成臃肿且低价值的全量矩阵；若同一根因或同一覆盖缺口已足以解释风险，可适度合并。
- 但仍需清楚说明哪些重要风险是覆盖充分、基本覆盖、覆盖不足、缺失、不适用或无法确认。

11）严重等级
- 每个问题必须标注严重级别：
  - Blocker
  - High
  - Medium
  - Low
- 优先报告独立根因级问题，而不是重复表层症状。
- 每个问题必须包含：
  - 严重级别
  - 结论
  - 证据
  - 影响
  - 最小可执行修复建议
  - 如有必要，给出最小验证路径或人工验证建议

12）禁止修改代码
- 本任务仅限审查。
- 不得为了让项目“看起来通过”而改代码。
- 如需修改，应仅记录在 “Issues / Suggestions” 中，不实际动代码。

====================
审查纪律

在输出任何强结论前，先自问：
- 这个结论是否有直接的 `file:line` 证据支持？
- 这是静态事实，还是我在暗示运行时行为？
- 我报告的是根因，还是只是在重复症状？
- 我是否是基于 AnuBook产品需求文档 在判断，而不是基于泛泛的个人偏好？
- 如果我不确定，这里是否应该写成“无法通过静态审查确认”？

你的优先级如下：
1. 找出真实的实质性缺陷
2. 保证结论有证据
3. 降低幻觉
4. 保持最终报告完整
5. 避免无意义重复
