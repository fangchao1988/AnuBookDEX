## 1. 总结结论

**Overall conclusion: Partial Pass**

项目包含一个生产级加密货币撮合引擎核心（`market-match.go`）且撮合逻辑测试覆盖良好，同时包含一份面向 Anubis Chain DEX 的改造方案和部分新模块骨架代码。但存在两个主要入口点、新 DEX 入口的依赖包（`chain/`）全部为 stub 实现（无法工作）、硬编码生产凭证泄露、无一类安全机制（认证/鉴权/隔离）等实质性问题。整体形态是"一个可运行的集中式撮合引擎 + 一份详细的 DEX 改造方案 + 部分骨架代码"的混合交付。

- `docs/DEX改造方案.md` 将 `chain/`、`ws/`、`rocksdb/` 明确标记为 Phase 1 任务项，这些模块目前是骨架/接口定义，不是可运行的实现

- 但 `market-match.go` (235 行) 包含了两个入口点中较大的一个，模块初始化逻辑与该文件耦合度较高

**证据：**

## 6. 安全审查摘要

### 认证入口

**结论：Fail**

- **理由**：整个项目中不存在任何认证机制。HTTP 端点无认证中间件，WebSocket 端点通过查询参数获取 `client_id` 但不验证身份。订单通过 MySQL 轮询获取，`UserId` 字段仅作为数据存储，无来源验证。
- **证据**：
  - `cmd/engine/main.go:43-50`（HTTP /health 无认证）
  - `cmd/engine/main.go:101`（HTTP /ws 无认证）
  - `ws/hub.go:163-186`（WebSocket upgrade 无认证）
  - `puller/puller.go:204`（UserId 仅从 DB 读取，无验证）

### 路由级鉴权

**结论：Fail**

- **理由**：无路由鉴权概念。HTTP 服务仅有两个端点（`/health` 和 `/ws`），WebSocket 升级后客户端可订阅任意 channel（`ws/hub.go:133`），无权限检查。
- **证据**：`ws/hub.go:133-143`（Subscribe 方法无权限检查）

### 对象级鉴权

**结论：Fail**

- **理由**：撮合引擎内部有 `UserId` 字段（`match/order.go:178`）并用于自成交预防（`match/matcher.go:917,1112`），但无任何逻辑验证"用户是否有权操作该订单"——订单来自 MySQL 序列表，系统信任表中数据。若序列表可被外部修改，则无防御层。
- **证据**：`match/order.go:178`；`match/matcher.go:552-554`（撤单仅通过 OrderId 查找，不校验 UserId）

### 函数级权限控制

**结论：不适用**

- **理由**：项目是后端引擎服务，无面向用户的函数级 API。所有内部函数调用均为同进程内调用。若未来暴露 RPC/HTTP API，则需此控制。

### 租户/用户数据隔离

**结论：Fail**

- **理由**：无多租户概念。所有交易对的订单簿共享同一进程内存（`match/order_book_map.go:4` 的全局 `OrderBookMap`），订单通过 `UserId` 区分但无隔离机制。撮合结果、行情数据全局广播（`ws/hub.go:93`），任何 WebSocket 客户端可订阅任意交易对数据。
- **证据**：
  - `match/order_book_map.go:4-5`（全局 OrderBookMap）
  - `ws/hub.go:93-103`（BroadcastDepth 对所有订阅者广播）
  - `ws/hub.go:133-143`（Subscribe 无隔离检查）

### 管理/内部/调试端点保护

**结论：Partial Pass**

- **理由**：`/health` 端点返回不含敏感信息的纯文本字符串（`cmd/engine/main.go:39-41`），这是合理设计。但无任何管理端点（如 metrics、pprof、config reload），因此管理端点保护在此阶段不适用。
- **证据**：`cmd/engine/main.go:39-41`
