## 一、交易类订单

<a id="market"></a>

### 1. Market 市价单（常量值 = 0）

**撮合函数**：[matcher.go:279 matchMarket](../internal/core/match/matcher.go#L279)

- **含义**：不指定价格，按当前市场最优价立即吃对手盘
- **买单是现金驱动**：`UnfilledAmount` 存现金金额（如 1000 USDT），撮合时通过 `cash / unitPrice` 换算成 token 数量（[matcher.go:1107-1113](../internal/core/match/matcher.go#L1107-L1113)）
- **卖单是数量驱动**：直接用 token 数量
- **不挂单**：对手盘耗尽时剩余部分取消，不留在订单簿上
- **有 CircuitRate 熔断保护**（[matcher.go:293-300](../internal/core/match/matcher.go#L293-L300)）：多档成交价偏离首笔成交价超过比例则停止撮合，剩余标记为 `CircuitCanceled`
- **精度保护**：剩余现金买不起 1 个 `LOWPRECISION`（0.01）单位时，标记为 `PrecisionCanceled`
- **最终状态**：`Filled`（完全成交）、`PartialCanceled`（部分成交后撤余）、`CircuitCanceled`（熔断）、`PrecisionCanceled`（精度不足）、`SelfTradeCanceled`/`SelfTradePartialCanceled`/`SelfTradeDecreased`（自成交预防触发）

---

<a id="limit"></a>

### 2. Limit 限价单（常量值 = 1）✅ 生产启用

**撮合函数**：[matcher.go:348 matchLimit](../internal/core/match/matcher.go#L348)

- **含义**：指定价格，**先吃后挂**——能成交的立即成交（taker），剩余部分挂在订单簿上（maker）等待后续对手方
- **价格检查**：通过 `matchAble(order, oppoOrder)` 判断价格是否满足成交条件（[matcher.go:192-198](../internal/core/match/matcher.go#L192-L198)），对手盘价不满足时调用 `book.Enqueue(order)` 插入红黑树
- **唯一会挂单的生产就绪类型**：未成交部分一直在簿上（GTC，Good-Till-Cancel 语义），等待主动撤单
- **最终状态**：`Submitted`（全部挂单未成交）、`PartialFilled`（部分成交后挂余）、`Filled`（全部成交不入簿）

---

<a id="ioc"></a>

### 3. IOC 立即成交撤余单（常量值 = 2）⚠️ 框架已实现，主入口未启用

**撮合函数**：[matcher.go:383 matchIoc](../internal/core/match/matcher.go#L383)

- **含义**：Immediate-or-Cancel，指定价格吃单，能成交多少成交多少，**剩余立即取消，不挂单**
- 与 Limit 的核心区别：Limit 吃不完挂单，IOC 吃不完撤余
- **注意**：[matcher.go:260-265](../internal/core/match/matcher.go#L260-L265) 中 `case Ioc` 被注释掉了，`matchIoc`/`matchOrderIoc`/`finalizeTakerIoc` 都已写好但未从主入口调度
- **最终状态**：`Filled`（全部成交）、`PartialCanceled`（部分成交后撤余）、`Canceled`（完全未成交）

---

<a id="fok"></a>

### 4. FOK 全成全撤单（常量值 = 5）✅ 生产启用

**撮合函数**：[matcher.go:472 matchFok](../internal/core/match/matcher.go#L472)
**预检查**：[matcher.go:405 canFilledFokOrder](../internal/core/match/matcher.go#L405)

- **含义**：Fill-or-Kill，**要么全部立即成交，要么全部不成交**（不做部分成交）
- **两步撮合**：
  1. **预检查**：遍历对手盘累加可成交量，如果累计量 < 订单量，**直接取消，不做任何成交**
  2. 预检查通过后才真正撮合
- 预检查也考虑 `CircuitRate`，价格超出熔断范围直接判定为不可成交
- 适用场景：大额吃单，防止被分批 front-run
- **最终状态**：`Filled`（全部成交）或 `Canceled`/`CircuitCanceled`（全不成交）

---

<a id="limit-maker"></a>

### 5. LimitMaker 做市单 / Post-Only（常量值 = 6）⚠️ 框架已实现，主入口未启用

**撮合函数**：[matcher.go:554 matchLimitMaker](../internal/core/match/matcher.go#L554)

- **含义**：**只做 Maker 不做 Taker**。如果挂单时对手盘已有可成交的单（即会成为 taker），**直接取消**，确保一定作为挂单方赚取 Maker 返佣、避免 Taker 手续费
- 逻辑：`oppoOrder == nil || !matchAble(order, oppoOrder)` → 挂单（Enqueue），否则 → `Canceled`
- **注意**：主 `Match()` switch 中没有 `case LimitMaker`，与 IOC 一样是函数已实现但未从主入口接入
- **最终状态**：`Submitted`（成功挂单）或 `Canceled`（会吃单，被拒绝）

<a id="sec-cancel"></a>

## 二、撤单类订单

<a id="cancel"></a>

### 6. Cancel 用户主动撤单（常量值 = 3）✅ 生产启用

**撮合函数**：[matcher.go:567 matchCancel](../internal/core/match/matcher.go#L567)

- **含义**：用户主动撤销自己之前挂的限价单
- 按 `OrderId` 通过 `cache map` O(1) 查找目标订单，找到后 `Dequeue` 从红黑树移除
- 根据目标订单当前状态返回结果：
  - `Submitted`（完全未成交）→ `canceled`
  - `PartialFilled`/`SelfTradeDecreased`（部分成交）→ `partial-canceled`
  - `Filled`（已完全成交）→ `filled`（撤单无效，订单早已成交）
  - 找不到目标订单 → `failed`

---

<a id="system-cancel"></a>

### 7. SystemCancel 系统撤单（常量值 = 4）⚠️ MVP 占位，未真正实现

**撮合函数**：[matcher.go:654 matchSystemCancel](../internal/core/match/matcher.go#L654)

- **含义**：由系统主动触发的撤单（而非用户发起），典型场景：
  - 仓位被强平时撤销该账户所有挂单
  - 涨跌停/熔断时系统批量撤销危险挂单
  - 上线/下线交易对时清空订单簿
- **当前实现是 stub**：直接返回一个 `canceled` 状态的 OrderResult，**没有** `Find` 目标订单、**没有** `Dequeue`，实际未从订单簿移除任何订单
- 生产级实现应与 `matchCancel` 类似，只是来源标记为系统，返回状态为 `system-canceled`（`OrderState` 中已定义 `SystemCanceled = 9`，[order.go:45](../internal/core/match/order.go#L45)），便于前端和审计区分撤单来源

---

<a id="batch-cancel"></a>

### 8. BatchCancel 批量撤单（常量值 = 13）✅ 生产启用

**撮合函数**：[matcher.go:607 matchBatchCancel](../internal/core/match/matcher.go#L607)
**数据结构**：[order.go:208-211 BatchCancelOrder](../internal/core/match/order.go#L208-L211)

- **含义**：一次请求撤销多个订单，减少多次请求的网络往返
- 订单的 `Extra` 字段存放 JSON 格式的 `[]BatchCancelOrder`（每个元素含 `OrderId` + `CancelState`）
- 遍历每个 OrderId，执行与 Cancel 相同的 Find → Dequeue → 返回状态逻辑
- 返回结果中包含每个子订单各自的撤单状态（`canceled`/`partial-canceled`/`filled`/`failed`）
- 典型应用：前端"一键撤单"、风控批量平仓

## 三、配套：5 种自成交预防（STP）模式

定义在 [order.go:74-82](../internal/core/match/order.go#L74-L82)，在 [matchAmountBasedOrderSelfTrade](../internal/core/match/matcher.go#L817)（数量模式）和 [matchCashAmountBasedOrderSelfTrade](../internal/core/match/matcher.go#L942)（现金模式）中处理。

| 值 | 常量 | 全称 | 等量相遇时 | 新单 > 旧单 | 新单 < 旧单 |
|----|------|------|-----------|-----------|-----------|
| 0 | AST | Allow Self-Trade | 成交 | 成交 | 成交 |
| 1 | DC | Decrease and Cancel | **双方都取消**（与 CB 等价） | 新单减量，旧单取消 | 新单取消，旧单减量 |
| 2 | CO | Cancel Old | 取消旧单，新单保留 | 取消旧单 | 取消旧单 |
| 3 | CN | Cancel New | **仅取消新单**，旧单保留 | 取消新单 | 取消新单 |
| 4 | CB | Cancel Both | 双方都取消 | 双方都取消 | 双方都取消 |

**做市商选 DC 的典型场景**：做市商在 100 USDT 挂买单 10 ETH（提供深度），同时用另一账户卖出 3 ETH 平仓——CB 会两单全撤导致深度消失（做市商需重新挂单再付手续费）；DC 只取消 3 ETH 的卖单、买单减至 7 ETH，深度得以保留。

> **陷阱点**：市价买单的现金模式 DC 逻辑比数量模式复杂——`UnfilledAmount` 是现金金额，需先除以 `unitPrice` 转成 token 数量再比较，中间涉及 `Truncate(0)` 精度处理。
